Request an evaluation Read the full evaluation protocol

What the evaluation covers

01 · SETUP

Confirm compatibility

Review Claude Code, Node.js, Git, operating system and repository prerequisites. Install the plugin in a controlled branch or disposable copy.

02 · POLICY

Define your contract

Set the goal, permitted file paths, protected files, shell allow-list and acceptance checks. Your team owns the contract.

03 · TEST

Exercise real scenarios

Run permitted work, out-of-scope attempts, approval-required actions, failed checks and post-receipt code changes.

04 · VERIFY

Check the evidence

Validate the receipt signature, evidence integrity, Git tree binding and CI gate result using a customer-controlled trusted key.

What your team receives

  • A record of the product version and tested environment.
  • The reviewed session contract and acceptance-check definitions.
  • Example receipts for the agreed scenarios.
  • Signature, code-tree and pull-request gate verification results where included.
  • A findings summary covering observed behaviour, false blocks, usability friction, missing coverage and unresolved limitations.
  • A recommendation for the tested workflow: proceed, remediate, or do not proceed.

The report applies only to the repository, versions, workflows and scenarios tested. It is not a security certification or a general assurance statement.

What your team needs

Environment

Claude Code, Node.js 20 or newer, Git, and one repository suitable for controlled testing.

Acceptance checks

Existing tests or acceptance commands representing the workflow being evaluated.

Ownership

A person responsible for the contract, approval decisions, signing key and trusted CI fingerprint.

Data stays under your control

The plugin runs locally and makes no network requests. Your team retains control of the repository, signing key, session logs and receipts. You decide which evidence to share and should redact it first.

Do not send source code, credentials, private keys, access tokens or unredacted environment files by email.

A signed receipt verifies integrity relative to a trusted public-key fingerprint. A signature does not prove that acceptance checks were truthful, well designed or run on an uncompromised host. Git tree comparison excludes gitignored files and the .receipts evidence directory by design.
